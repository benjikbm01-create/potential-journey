# Underdeep — instructions for Claude Code sessions

Underdeep is a Minecraft Java 1.21.1 Fabric mod (mod id `underdeep`): a cooperative underground
survival sandbox for 4–6 friends over ~two weeks. The entire world is underground: vast
interconnected caverns with ecosystems, civilizations, wildlife and history that live on
independently of the players. Players are inhabitants, not chosen heroes.

## Read first (every session)

1. This file.
2. `docs/PROGRESS.md` (what exists), `docs/NEXT_STEPS.md` (what to do now), `docs/TESTING.md`.
3. `docs/ARCHITECTURE.md` for the systems you will touch; `docs/MASTER_DESIGN.md` for intent;
   `docs/DECISIONS.md` before changing an established approach; `docs/CONTENT_REGISTRY.md` when
   adding content.
4. Inspect the code you will change, then run `./gradlew build` (and the tests) BEFORE making major
   changes so you know the starting state.
5. Identify the exact scope of the assigned stage. Do not start later stages.

## Technical requirements

- Minecraft 1.21.1, Fabric Loader 0.17.3, Fabric API 0.116.18+1.21.1, Yarn 1.21.1+build.3,
  Loom 1.11.8, Gradle 8.14.3 (wrapper), Java 21. Versions are pinned in `gradle.properties`.
- Dedicated server and singleplayer must both work. Target 4–6 players, 6–10 GB server heap,
  stable 20 TPS. No paid APIs, no external services, no unnecessary dependencies.
- The build host rate-limits Maven Central: Gradle retries are configured in `gradle.properties`;
  use `--offline` once dependencies are cached.

## Architectural principles

- **The terrain model is a pure function** of (seed, x, y, z): `world/terrain/UnderdeepTerrain`.
  Never make world generation depend on chunk generation order or on other chunks. Anything a later
  system needs to know about unloaded areas should come from the model, not from loading chunks.
- **Tiered simulation** (later stages): detailed entities near players, aggregate simulation far
  away, persistent abstract state for unloaded settlements/populations/caravans keyed by stable ids
  (`RegionId`, future `SettlementId`, ...). Never force-load chunks to simulate distant activity.
- Thread safety: worldgen runs on worker threads. Shared state must be immutable; caches are
  thread-local. Features may only write inside their 3x3 chunk window.
- Persistence contracts (enum ids/ordinals of `RegionType`, `CavernLayer`, `SiteType`, packed
  `RegionId`, `UnderdeepWorldState` NBT keys) are append-only. Changing terrain output requires
  bumping `UnderdeepTerrain.GENERATOR_VERSION` and documenting it in `docs/DECISIONS.md`.
- Prefer data (JSON worldgen generated by `tools/worldgen/generate_data.py`) for content lists;
  Java for systems. Edit the generator script, re-run it, and commit both.
- Build working depth before breadth. Never sacrifice a working system for many unfinished ones.
- Keep debugging utilities separate from gameplay: `/underdeep` commands are permission-gated;
  self-test and screenshot tour are enabled only by JVM system properties.

## Development workflow

- Work in small verified steps; keep the project compiling. Use git; commit completed work.
- Do not push to a remote or publish secrets unless the user explicitly asks.
- Fix discovered defects rather than papering over them; preserve previously working features.
- If context or usage limits approach, stop at a stable checkpoint, update docs (especially
  `NEXT_STEPS.md`) and commit.

## Testing requirements

- Unit tests: `./gradlew test` (pure terrain model; fast). Add tests for new pure logic.
- Dedicated server self-test: `scripts/selftest.sh <seed> <run-dir> [create|reload] [forward|reverse]`
  (see `docs/TESTING.md`). Run at least three seeds for worldgen changes; run `reload` to verify
  persistence; compare chunk hashes between orders for determinism.
- Visual inspection: `scripts/visual_tour.sh` runs a real client under Xvfb and saves screenshots.
- Mob populations: `scripts/mob_study.sh <run-dir>` (real client joins the dedicated server).
- Full matrix: `scripts/test_matrix.sh` (seeds, reload, chunk-order determinism, vanilla, production JAR).
- Stage 2+ targeted suite: `SUITE=stage2 scripts/selftest.sh …` and `scripts/stage2_matrix.sh` (skips the slow
  terrain analyses; use the full matrix when terrain output changes). Keep individual runs time-limited.
- Assets: `python3 tools/assets/stage2_assets.py` regenerates all block/item assets (it runs
  `generate_assets.py` first and includes `creatures.py`); content ids must match `registry/Mod*` and
  `wildlife/WildlifeRegistry`. Ecology metadata lives in `ecology/EcologyRegistry`, wildlife species in
  `wildlife/WildlifeRegistry` (both append-only ids).
- Wildlife (Stage 3): wild animals are owned by their region's abstract population (`RegionWildlife`), never
  by chunks; keep the invariant "active entities ≤ regional count" and never save wild entities. Behaviour
  tests in `debug/Stage3Checks` tick entities directly (accelerated) — say so when reporting them.
- Civilizations (Stage 4): settlement placement and plans are pure functions of the seed and terrain model
  (`SettlementMap`, `SettlementPlanner`); chunks only write their share of a plan. Settlements generate only in
  worlds created with generator v3+. Inhabitants are persistent records embodied near players and never saved
  as entities. Judge architecture with `GALLERY=true` + `scripts/visual_tour.sh`, never from compilation alone.
  Asset scripts must be deterministic (no Python `hash()`): set `PYTHONHASHSEED=0` when re-running `creatures.py`.
- Inhabitant minds (Stage 5): personality, needs, memories, relationships, goals and companion state live in the
  record's `Mind` (`civ/mind`, schema `Mind.SCHEMA`, append-only ordinals); the same `Brain` drives embodied and
  abstract inhabitants. Dialogue is an authored topic library (`civ/npc/Topics`) — every topic must only state
  things that are true for the speaker. See `docs/NPC_MINDS.md`. Operators inspect minds with `/underdeep npc …`.
- Economy (Stage 6): one `Economy` per settlement in `EconomyState` (`civ/econ`); goods/recipes are data generated by
  `tools/economy/generate_economy.py` (real item ids only). Every money or goods movement goes through validated
  transfers; keep the world money audit (`/underdeep econ audit`, Stage6Checks) exact. Construction must never
  overwrite non-natural blocks. See `docs/ECONOMY.md`.
- Survival (Stage 7): content (foods, drinks, medicine, materials, station recipes) is data generated by
  `tools/assets/stage7.py` (run via `stage2_assets.py`); the economy imports it. Stations consume inputs once at
  completion; buffs are bounded (`Meals.apply`); hazards are exposure meters that never apply in starting regions.
  Per-player state is the `SurvivalData` attachment (append-only keys). See `docs/SURVIVAL.md`.
- Equipment (Stage 8): materials, weapons, armour, tools, accessories, upgrades, components and the processing/forge
  recipes are data generated by `tools/assets/stage8.py` (+ `stage8_art.py`, run via `stage2_assets.py`); Java in
  `equipment/`. Upgrade effects are always recomputed from the base item (`Upgrades.recompute`), accessory modifiers use
  stable ids and are removed before re-adding — never let attributes accumulate. Salvage must return less than crafting
  costs. See `docs/EQUIPMENT.md`.
- Exploration (Stage 9): site placement is a pure function of the seed and terrain model (`explore/ExplorationMap`);
  layouts are authored in `explore/design` (`Kit`, `Style`) and must pass the static audit (`LayoutAudit`, run by
  `SUITE=stage9 scripts/selftest.sh <seed> <dir> create`, ~2–3 min). Mechanisms are indexed by `SiteLayout` (no block
  entities); player-caused state lives in `ExplorationState`/`ExplorerData` (append-only keys). Rewards follow the
  shared/personal/unique/key policies (claims before items). Family/secret/record content is data generated by
  `tools/assets/stage9.py` (+ `stage9_art.py`, run via `stage2_assets.py`). Places, secrets and records are shown
  to players only after discovery. See `docs/EXPLORATION.md`; solutions and identities only in `docs/private/`.
- Caves (Stage 10): the secondary passage network (`world/terrain/Passages`) and descent caves (`Descents`) are part of the
  pure terrain model and exist only for generator v5+ (`UnderdeepTerrain(seed, version)`; older worlds keep their
  terrain). Validate physical routes with `VoxelWalk` (model) and the `stage10` suite (generated blocks), never with a
  graph alone. See `docs/CAVES.md`.
- Combat (Stage 10): server-authoritative layer in `combat/` (stamina, dodge, heavy attacks, parries, counters, poise);
  clients send intents only. Creature fighting uses `CombatGoal` + `Archetype` (every attack telegraphed, recovery
  windows). Guardians live in `boss/` (framework, `Brains`, `Lairs`, `Encounters`, `Ending`); they are never saved as
  entities, scaling only rises, claims are recorded before rewards. Every boss move must have a wind-up and every
  guardian a ranged answer. Identities, mechanics and the ending are private (`docs/private/BOSSES.md`); public docs
  give counts and architecture only. Self-test: `SUITE=stage10 scripts/selftest.sh <seed> <dir> create`. See
  `docs/COMBAT.md`.
- Visuals and audio (Stage 11):
  - Creatures are hand-authored designs (`tools/assets/creature_designs.py`) on the anatomy kit (`creature_kit.py`),
    animated by role in `client/creature/CreatureModel`.
  - Inspect every model change with `tools/preview/render_models.py` and the zoo tour. Guardian previews stay in
    `docs/private/previews/`.
  - The soundtrack is code: run `tools/music/compose.py` (73 tracks, analysis in `tools/music/out/manifest.json`).
    `MusicDirector` picks music by context; the server only hints settlement and home (`audio/MusicContext`).
  - Never claim audio was listened to, or animation watched, unless it was. Update `docs/ASSET_QUALITY.md` (run
    `tools/preview/asset_audit.py --from-screenshots`). See `docs/ART_DIRECTION.md` and `docs/SOUNDTRACK.md`.
- **Permanent requirement: model quality (Stage 11, top priority).** The owner considers the current models poor. Stage
  11 must rebuild creatures, bosses, NPCs, armour, weapons, tools, plants, furniture, workstations and decorative models
  with handcrafted Blockbench-style geometry (distinctive silhouettes, believable anatomy, articulation, natural
  animation, careful texture mapping; Alex's Mobs / BetterEnd / Create as quality benchmarks, never copied), verified
  model by model in-game. Registration is not proof of quality; spoiler-sensitive previews stay private.
- **Permanent requirement: continuous soundtrack (Stage 11).** Underdeep must have continuous music (about 60–80
  original tracks across ecosystems, layers, civilizations, exploration contexts, danger and calm) with crossfades
  on context changes, plus a client option for vanilla-style gaps. Later stages must expose an audio context for
  new places (as Stage 9 does with `underdeep:explore_context`).
- **Permanent requirements for every new stage (Stage 8 onward):**
  - **Obtainability**: every new item must be reachable in the audit (`guide/Obtainability`; `SUITE=audit
    scripts/selftest.sh <seed> <dir>`, ~1.5 min), have a use, and not create circular dependencies; secret items are
    listed as `deferred` in `data/underdeep/guide/visibility.json` and explained only in `docs/private/`. See
    `docs/RESOURCES.md`.
  - **Handbook**: every new player-facing system gets tutorial/reference pages in `tools/handbook/handbook.py`
    (re-run it; it validates links and ids). Item pages are generated from real data — never hand-write acquisition
    facts. Discovery-sensitive pages use `req` keys. See `docs/HANDBOOK.md`.
  - **Advancements**: report completed actions with `guide/Advancements.event(player, event, subject)` and add
    advancements in `tools/advancements/generate.py` (re-run it). Spoiler advancements are `hidden`; rewards only once;
    migrations must be quiet and evidence-based.
- Worldgen output changes require bumping `UnderdeepTerrain.GENERATOR_VERSION` (currently 5) and telling the
  user that existing worlds must be regenerated. Never delete or overwrite the user's worlds.
- **Never record a test as passing unless it was actually executed.** Record commands, environment
  and results in `docs/TESTING.md`, including failures and things not tested.

## Spoiler protection

The user intends to play the mod without knowing its secrets. Secret lore, hidden discoveries,
unique encounters and other spoiler-sensitive design live only in `docs/private/`. Never reveal
`docs/private/` content in user-facing summaries, commit messages or public docs. Public docs may
say that private material exists, not what it contains.

## Completion standards

A stage is complete only when its requirements are implemented, built, tested (results recorded),
documented (`PROGRESS`, `TESTING`, `NEXT_STEPS`, `DECISIONS`, `CONTENT_REGISTRY` updated), a
development JAR is produced (`build/libs/underdeep-<version>.jar`) and the work is committed. If
something is not done, say so precisely; never declare completion with major requirements missing.
End each session with a concise, spoiler-free report.
