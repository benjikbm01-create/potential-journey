# Underdeep — instructions for Claude Code sessions

Underdeep is a Minecraft Java 1.21.1 Fabric mod (mod id `underdeep`): a cooperative underground
survival sandbox for 4–6 friends over ~two weeks. The entire world is underground: vast
interconnected caverns with ecosystems, civilizations, wildlife and history that live on
independently of the players. Players are inhabitants, not chosen heroes.

## Read first (every session)

1. This file.
2. `docs/PROGRESS.md` (what exists), `docs/NEXT_STEPS.md` (what to do now), `docs/TESTING.md`.
3. `docs/ARCHITECTURE.md` for the systems you will touch; `docs/MASTER_DESIGN.md` for intent;
   `docs/DECISIONS.md` before changing an established approach; `docs/CONTENT_REGISTRY.md` when
   adding content.
4. Inspect the code you will change, then run `./gradlew build` (and the tests) BEFORE making major
   changes so you know the starting state.
5. Identify the exact scope of the assigned stage. Do not start later stages.

## Technical requirements

- Minecraft 1.21.1, Fabric Loader 0.17.3, Fabric API 0.116.18+1.21.1, Yarn 1.21.1+build.3,
  Loom 1.11.8, Gradle 8.14.3 (wrapper), Java 21. Versions are pinned in `gradle.properties`.
- Dedicated server and singleplayer must both work. Target 4–6 players, 6–10 GB server heap,
  stable 20 TPS. No paid APIs, no external services, no unnecessary dependencies.
- The build host rate-limits Maven Central: Gradle retries are configured in `gradle.properties`;
  use `--offline` once dependencies are cached.

## Architectural principles

- **The terrain model is a pure function** of (seed, x, y, z): `world/terrain/UnderdeepTerrain`.
  Never make world generation depend on chunk generation order or on other chunks. Anything a later
  system needs to know about unloaded areas should come from the model, not from loading chunks.
- **Tiered simulation** (later stages): detailed entities near players, aggregate simulation far
  away, persistent abstract state for unloaded settlements/populations/caravans keyed by stable ids
  (`RegionId`, future `SettlementId`, ...). Never force-load chunks to simulate distant activity.
- Thread safety: worldgen runs on worker threads. Shared state must be immutable; caches are
  thread-local. Features may only write inside their 3x3 chunk window.
- Persistence contracts (enum ids/ordinals of `RegionType`, `CavernLayer`, `SiteType`, packed
  `RegionId`, `UnderdeepWorldState` NBT keys) are append-only. Changing terrain output requires
  bumping `UnderdeepTerrain.GENERATOR_VERSION` and documenting it in `docs/DECISIONS.md`.
- Prefer data (JSON worldgen generated by `tools/worldgen/generate_data.py`) for content lists;
  Java for systems. Edit the generator script, re-run it, and commit both.
- Build working depth before breadth. Never sacrifice a working system for many unfinished ones.
- Keep debugging utilities separate from gameplay: `/underdeep` commands are permission-gated;
  self-test and screenshot tour are enabled only by JVM system properties.

## Development workflow

- Work in small verified steps; keep the project compiling. Use git; commit completed work.
- Do not push to a remote or publish secrets unless the user explicitly asks.
- Fix discovered defects rather than papering over them; preserve previously working features.
- If context or usage limits approach, stop at a stable checkpoint, update docs (especially
  `NEXT_STEPS.md`) and commit.

## Testing requirements

- Unit tests: `./gradlew test` (pure terrain model; fast). Add tests for new pure logic.
- Dedicated server self-test: `scripts/selftest.sh <seed> <run-dir> [create|reload] [forward|reverse]`
  (see `docs/TESTING.md`). Run at least three seeds for worldgen changes; run `reload` to verify
  persistence; compare chunk hashes between orders for determinism.
- Visual inspection: `scripts/visual_tour.sh` runs a real client under Xvfb and saves screenshots.
- **Never record a test as passing unless it was actually executed.** Record commands, environment
  and results in `docs/TESTING.md`, including failures and things not tested.

## Spoiler protection

The user intends to play the mod without knowing its secrets. Secret lore, hidden discoveries,
unique encounters and other spoiler-sensitive design live only in `docs/private/`. Never reveal
`docs/private/` content in user-facing summaries, commit messages or public docs. Public docs may
say that private material exists, not what it contains.

## Completion standards

A stage is complete only when its requirements are implemented, built, tested (results recorded),
documented (`PROGRESS`, `TESTING`, `NEXT_STEPS`, `DECISIONS`, `CONTENT_REGISTRY` updated), a
development JAR is produced (`build/libs/underdeep-<version>.jar`) and the work is committed. If
something is not done, say so precisely; never declare completion with major requirements missing.
End each session with a concise, spoiler-free report.
